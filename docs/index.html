十年老提案落地：Go 1.28 将允许省略复合字面量中的类型
Damien Neil 于 2015 年提出的复合字面量类型推断提案，在历经十余年、约 260 条评论的讨论后终于被接受，将随 Go 1.28（2027 年 2 月）落地。它在可赋值性规则中新增一条：凡是 Go 已知所需类型的位置——返回值、结构体字段、函数参数、赋值、channel 发送——都可以直接写 {...} 省略类型；期望指针时 {...} 会被解释为 &T{...}。在 := 声明、any 类型变量和泛型类型参数处仍会编译报错。尽管 Alan Donovan 认为激进省略类型的代码「难读得多」，审查组仍接受了宽松规则，gofmt/gopls 也不会进一步删除类型。现在可通过 gotip 加 go 1.28 模块指令试用。

Go 默认 HTTP 客户端的性能损耗（以及一点内核探秘）
作者对 Go 默认 HTTP 客户端做基准测试发现：每个主机的空闲连接上限仅为 2，这对 HTTP/1.1 是严重瓶颈——每个进行中的请求都需要独占一条连接。将 MaxIdleConnsPerHost 提到与 worker 数一致后，64 并发下吞吐从 2721 提升到 22922 req/s（约 8 倍），客户端 CPU 占用也减半以上。用 perf 分析显示内核时间大多耗在为出站连接分配本地端口的 __inet_hash_connect 上：客户端每秒新建约 1600 条连接，叠加 60 秒 TIME_WAIT 后端口供不应求；又因 Linux 偏好偶数端口，空闲端口几乎全是奇数，导致每次 connect() 都要先扫描数千个不可用的偶数端口——每秒超过 2000 万次端口检查。

gopgext：用 Go 编写 PostgreSQL 扩展
gopgext 是一个实验性工具，借助 TinyGo 把用普通 Go 代码写就的 PostgreSQL 扩展编译为原生扩展（用 TinyGo 而非 cgo 是关键：完整 Go 运行时的后台线程与 PostgreSQL 进程模型冲突）。开发者只需在函数上加 //gopgext:function 注释，工具就会自动生成所需的 C 胶水代码、安装脚本和 control 文件；Go 标准库可在扩展内使用，Go 类型（字符串、数值、数组、JSON 及自定义复合类型）会自动映射到 SQL 类型。除函数外还支持触发器、聚合、GiST/GIN/SP-GiST/BRIN 算符类、索引访问方法、外部数据封装器和查询钩子，pgcrypto、hstore 等 contrib 模块的移植版已通过上游回归测试。作者提醒：生成代码的 bug 会直接跑在服务器进程内，请勿用于生产环境。

mamori 介绍：Go 的类型化、可监听配置与密钥库
mamori（日语「守护」）是一个开源 Go 库（MIT，v0.1.0，要求 Go 1.26+），可将来自 30 多种来源（AWS Secrets Manager、Vault、GCP/Azure 密钥管理、K8s Secret/ConfigMap、Consul、1Password、SOPS、各类数据库与特性开关平台等）的配置和密钥加载进类型化结构体，并在运行时持续对账、无需重启。核心概念是 source 标签引用（如 env:LOG_LEVEL、aws-sm://prod/db#password）、仿 database/sql 驱动模式按 scheme 注册的 Provider（核心零云 SDK 依赖），以及 Reconciler：值变更时重新验证整个结构体，只有全部合法才原子替换并触发带 diff 的 OnChange 回调。secret.String/secret.Bytes 类型在日志、JSON、slog 中自动脱敏，配套 go vet 分析器强制密钥字段使用安全类型，另带缓存/故障转移/审计/限流中间件和 OTel 可观测性桥接。

在单台 VM 上跑 1500 万个 Web 服务器：smoltcp、DPDK 与 AF_XDP
作者尝试在一台仅有 10GB 内存、单核 CPU 的 VM 上运行 1500 万个 Web 服务器，但直接撞上 Linux 内核限制：默认 ip_local_port_range 会耗尽端口，且每个 socket 在 tcp_sock、socket_alloc 等内核结构上要占约 3300 字节。解法是把整个网络栈搬到用户态：用 Rust 的 TCP/IP 实现 smoltcp 配合自定义运行时（LFI 沙箱，每个来宾仅约 16 字节状态），收发包走 TUN/TAP、DPDK、AF_XDP 等内核旁路技术——DPDK 直接内存映射网卡、零系统调用，AF_XDP 在设备仍归内核的前提下达到相近效果。最终每个空闲服务器仅占约 620 字节内存，成功跑起 1600 万个服务器，DPDK 在基准测试中领先。

Belay：为数据库变更做形式化验证
Belay 是一个概念验证性的 Lean 库（目前支持 SQLite），把形式化验证引入数据库 schema 迁移。工作流是：你声明必须始终成立的不变量，编码 Agent 每写一个迁移都必须同时给出「该迁移保持不变量成立」的证明，由 Lean 的证明检查器校验——因此该保证对所有具有此 schema 的数据库都成立，而不只是被测过的那几个实例。20 秒演示中，检查器先找出一个会让迁移丢数据的数据库，再验证修正后的迁移确实保住了数据。

Slack 实时消息系统架构：Real-time Messaging

derive(Debug) 的编译期改进
文章讲述优化 Rust 编译器中 derive(Debug) 的过程：大型 enum 生成的含字符串字面量的 match 会带来二次复杂度的 match 检查和超线性的借用检查开销。第一版修复（把变体名拼成一个字符串、按判别式索引）因 crater 运行发现 bitflags 回归而被回退——这类宏会改写判别式，属于 TOCTOU 式的宏问题。重新落地时改为让 match 返回小整数索引（借用检查更便宜）并去掉生成的索引数组，改由 std 辅助函数按空格分隔查找名字边界；这又触发 MSP430 嵌入式平台的二进制体积回归，最终用自定义 ASCII 切分例程修复。同一拼接字符串策略扩展到结构体后，ripgrep 等 crate 的编译时间明显下降，后续还计划优化更复杂的 enum 和 match 检查算法本身。

负载越高反而越快：调优 Postgres 只读副本
在 ClickHouse Managed Postgres 上的测试表明，基于归档传送的副本延迟随吞吐量呈 U 形曲线：WAL 段要攒满 16MB 或等 60 秒超时才会发送，太闲的系统也可能滞后近一分钟。基础调优（archive_timeout=5s、wal_retrieve_retry_interval=500ms）可把延迟压到几秒，但每次轮询都迫使副本从对象存储重新拉取并解压段，推高 CPU 占用。更激进的技巧（循环执行 pg_switch_wal()、经 WAL-G 守护进程路由拉取）能进一步降低延迟，但要以约 15% 的主库吞吐为代价，还可能带来可观的跨 AZ 网络账单。即便如此，流式复制在延迟上仍胜过所有归档调优方案；但作者认为归档传送仍是更好的默认选择，因为流式复制存在 hot_standby_feedback 拖慢 vacuum、复制槽可能撑爆主库磁盘等陷阱。

软件是否从一开始就复杂到超出了人类的能力？
作者由 AI 辅助、Lean 验证的黎曼猜想证明（约 1700 万行代码、尚无人类完全读懂）谈起，指出人类在理论理解跟不上的情况下已把软件铺满整个社会，近年频发的大范围同时故障和安全漏洞正是佐证——我们可能高估了人类写软件的能力。他提出两条对策：其一，所有新软件（乃至重建的操作系统栈和指令集）都应从形式化规格推导得出；其二，刻意为系统引入多样性，让单个 bug 无法同时攻陷海量主机。作者强调仅靠更好的 AI 模型只会产出「堆积如山的 slop 代码」，人类仍需决定规格里装什么；开源社区也仍在与 AI 披露和信任问题搏斗。

GLM-5.4：首个 Loop Transformer 旗舰模型，迈向通用化编码
GLM-5.4 是 Z.ai 首个基于 Loop Transformer 架构的旗舰模型：让 GLM-5 基座中 28 层权重共享的层迭代执行两遍、反复精炼隐状态，在不增加参数的情况下获得更深推理能力，750B 规模即达到 2T-3T 参数模型的智能水平。关键工程设计包括逐 token 门控渐进更新（防止激活范数爆炸）、全局共享+独立滑动窗口的混合 KV 缓存（1M 上下文下部署成本增幅可控）以及稀疏注意力索引复用。30B 同参数对照实验显示仅多约 10% 训练算力即有明显收益，数学、科学推理与长上下文任务提升最大，多数基准的输出长度还缩短 10-14%；推理峰值速度 70-80 tokens/s、低谷可达 200。它标志着「通用化编码（Generalized Coding）」的起点——用代码生成/编辑视频、构建完整游戏、3D 建模与机械设计；已知局限是容易陷入过长的「马拉松式思考」。模型权重计划在安全加固后开源。
